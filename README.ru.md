# Hatch для VS Code

Структурные патчи для исходного кода прямо в редакторе. Вместо номеров строк патч
[Hatch](https://github.com/Danil-Varakin/hatchTs) описывает, *где* менять код, в
терминах структуры самого кода, а инструмент находит это место.

> English version: [README.md](./README.md)

Расширение делает две вещи:

- **Порождает патч по вашим правкам.** Новая версия — то, что сейчас в редакторе, включая
  несохранённое. Старая — файл, каким он последний раз сохранён на диске, или ревизия git,
  если её называет конфиг проекта или ваши настройки.
- **Переключает между патчем и кодом, к которому он относится.** `alt+O` (на macOS `⌥⌘O`) уводит на
  другую сторону — из кода, из патча или из половины диффа с базой; `alt+B`
  (`⌥⌘B`) открывает базу
  и показывает, что ханк заменяет. Какой патч к
  какому файлу относится, отвечает ядро — по `Target` в шапке патча, дереву патчей или
  `generate.out`, — поэтому навигация работает сразу после открытия редактора, без
  генерации.

Нужен hatch с протоколом 4 — hatch 0.4.1 и новее. Ядро едет внутри расширения и
запускается отдельным процессом; из клона это соседний клон ядра
(см. [Разработка](#разработка)).

## Что нужно

- VS Code 1.101 и новее — ядро работает на его Node 22.
- Ядро Hatch запускается отдельным процессом и едет с расширением зависимостью.
  Используется тот же Node, на котором работает сам редактор, поэтому установленный в
  системе Node не нужен.
- Грамматики tree-sitter — ставить ничего не нужно. С hatch 0.4 они лежат внутри пакета
  самого ядра (`node_modules/hatch/grammars`), поэтому патч порождается без сети и ничего
  никогда не скачивается. Своя грамматика кладётся в `HATCH_GRAMMAR_DIR` — ядро смотрит
  туда первым и всё равно держится пина.

## Команды

| Команда | Что делает |
|---|---|
| **Hatch: Generate Patch** (`alt+G`, на macOS `⌥⌘G`) | пишет патч туда, куда проект кладёт патчи — по умолчанию `<файл>.hatch` рядом с файлом, — и открывает его сбоку |
| **Hatch: Go to the Other Side** (`alt+O`, на macOS `⌥⌘O`) | из ханка — в код, который он меняет, и обратно из кода — в его ханк |
| **Hatch: Go to What the Hunk Replaces** (`alt+B`, на macOS `⌥⌘B`) | открывает diff «база ↔ база + патч», ханк выделен с обеих сторон |
| **Hatch: Preview Patch** | тот же diff для всего патча, из патча или из его кода: что запишет сборка, ничего не записывая |
| **Hatch: Check All Patches** | все `.hatch` workspace против базы проекта или названной ветки, тега, коммита — в панели **Hatch Patches** в Explorer |
| **Hatch: Copy Patch Report** | последняя проверка в Markdown: итог и каждый патч, на который надо посмотреть |
| **Hatch: Open Failed Patches** | открывает все патчи, которые последняя проверка нашла неприменимыми |
| **Hatch: Show Edits Not in Patch** | diff «база + патч ↔ файл»: правки в коде, которых патч не пишет |
| **Hatch: Generate Patch Against File…** | выбрать старый файл и сгенерировать патч от него, один раз |
| **Hatch: Show Base** | показать, с какой базой сравнит генерация из активного файла и откуда это взялось |
| **Hatch: Init Config** | создаёт минимальный `hatch.config.json` в корне репозитория и открывает его; существующий только открывает |
| **Hatch: Show Log** | открыть канал вывода Hatch |

Три сочетания, по три клавиши: `⌥⌘G`, `⌥⌘O`, `⌥⌘B` на macOS и `alt+G`, `alt+O`,
`alt+B` на остальных. На macOS один Option печатает символ — `alt+O` это `ø`, — а Control
его надёжно не подавляет, поэтому Command есть в каждом macOS-сочетании. Shift там не
используется: переход в четыре клавиши не нужен никому. Команды без сочетания есть в
палитре; назначить или переназначить — в **Preferences: Open Keyboard Shortcuts**.

Расширение запускается, когда в workspace есть `hatch.config.json`, когда открыт
Markdown-файл или по первой команде Hatch — а не в каждом окне.

## Что видно в патче

Откройте патч — его состояние видно без единой команды и пересчитывается, пока вы правите
патч, код или базу.

`.hatch` — свой язык: шапка, заголовки, операторы `...` `>>>` `<<<` внутри `# match` и
заметки подсвечены, а код внутри ханка — как язык из его заголовка (Kotlin — только с
расширением, которое приносит грамматику Kotlin). Ханки и заметки сворачиваются; Outline и
хлебные крошки показывают ханки с их состоянием; на `match` и `note` есть сниппеты.
Хвостовые пробелы в патче значимы, поэтому в `.hatch` они видны и не обрезаются, а
форматирование при сохранении выключено.

Над каждым `# match` — строка с состоянием ханка и местом, куда он ложится; клик ведёт
туда (то же, что Go to the Other Side):

| Линза | Что значит |
|---|---|
| `✓ src/a.cc:413` | в коде лежит то, что пишет ханк, на этой строке |
| `✓ src/a.cc:413 · depends on an earlier hunk` | то же; его цель появляется только после более раннего ханка |
| `○ not applied · src/a.cc:410` | код всё ещё равен базе: патча в нём нет, строка — куда он встал бы |
| `◌ nothing to check: src/a.cc has no unsaved edits` | база — сохранённый файл, и код равен ему: есть ли в нём патч, сказать нельзя; с git-базой — можно |
| `⚠ differs from the code — regenerate?` | ханк ложится, но код в этом месте уже другой |
| `✗ anchor 3 of 5 not found` | шаблон остановился на якоре, которого в базе нет |
| `✗ fits 4 places` | шаблон неоднозначен: нужно больше контекста |

Сломанный якорь подчёркнут на своей строке, причина — в **Problems**; ханк, который никуда
не лёг, подсвечен красным фоном, ханк, текста которого в коде больше нет, — жёлтым, оба с
меткой на полосе прокрутки. Если не разрешается вообще ничего — нет файла, нет базы, —
одна строка вверху патча говорит почему, и Problems показывает это на шапке. Патч, чьего
файла больше нет в апстриме, — **осиротевший**: ему не к чему применяться, и **Delete
Patch…** после подтверждения отправляет его в корзину. Если ветки или коммита базы нет в
репозитории, расширение просит сделать fetch.

На сломанном или съехавшем ханке лампочка (`ctrl+.`) предлагает подходящие действия:
**Show How Far It Got**, **Show the N Places It Fits…**, **Go to the Earlier Hunk**,
**Regenerate Patch**. Сначала те, что только показывают; переписывающее никогда не стоит по
умолчанию.

Строка состояния показывает `Hatch: 3/4 hunks` для патча (клик — журнал последнего
разрешения) а для файла кода с патчем — сторожа: `matches its patch`, `edits not in the patch` (сборка
из патча их потеряет) или `patch not applied`; для файла без патча — его базу (клик —
**Show Base**). В workspace без
`hatch.config.json` и без открытого `.hatch` расширение молчит и не запускает ядро, пока не
выполнена команда Hatch.

**Generate Patch** предлагается на файлах, для которых у ядра есть грамматика; на других
он говорит об этом, ничего не отправляя, если язык не задан в `hatch.language`. Прогресс
показывает прошедшее время. Канал **Hatch** в Output пишет, что произошло и сколько это
заняло у ядра; сообщения обмена с ядром — в них куски ваших файлов — видны только на уровне
*Trace* (**Developer: Set Log Level…**).

## Откуда берётся база

По умолчанию — сам файл, каким он сохранён на диске. Тогда патч описывает ровно те
правки, которые вы ещё не сохранили, и настраивать ничего не нужно.

Проект, который сравнивает с git, пишет это один раз в `hatch.config.json` (схема 2):

```jsonc
{ "version": 2, "generate": { "base": { "head": true } } }   // или "branch": "main", "commit": "…"
```

Тогда буфер сравнивается с файлом в этой ревизии — здесь с последним коммитом текущей
ветки. `hatch.base.head`, `hatch.base.branch` и `hatch.base.commit` делают то же только
для вас, а `hatch.base.head: false` возвращает сохранённый файл, что бы ни говорил
конфиг. Статус-бар показывает базу активного файла (`base HEAD:src/a.cc @ 4f1c2e2`) и
пересчитывает её после коммита или смены ветки.

База из git читается **с окончаниями строк файла на диске**, если `generate.base.eol` или
`hatch.base.eol` не говорят иного: при `core.autocrlf` git хранит LF, а в файле CRLF, и
сравнение пометило бы изменённой каждую строку. CLI по умолчанию берёт `repository`;
редактор сравнивает с буфером, а буфер — это диск.

Если патчить нечего, так и сказано — `a.cc matches HEAD:src/a.cc, nothing to patch`, — и
патч не пишется.

**Hatch: Generate Patch Against File…** спрашивает старый файл и сравнивает
буфер с ним — как `--in-old` в CLI. Только для этого запуска: ничего не запоминается,
следующий **Generate Patch** и навигация снова сравнивают с сохранённым файлом.

Если базу использовать не удалось, сообщение говорит почему и предлагает выбрать старый
файл вручную. База из git, которую пока нельзя прочитать — файл ещё не закоммичен, ветки
нет, — так и называется, в сообщении и в строке состояния, и никогда не подменяется
сохранённым файлом. **Hatch: Show Base** в любой момент пишет в лог базу активного файла и
откуда взялась каждая настройка `generate.base`.

## Куда попадают патчи

Патч — это файл `.hatch`. По умолчанию он лежит рядом со своим файлом: у `src/a/b.cc`
появляется `src/a/b.cc.hatch`.

`generate.out` переносит его. Значение **без расширения** (или со слешем на конце, или
указывающее на существующую папку) — это директория, в неё кладётся `<имя файла>.hatch`;
файл должен называться `*.hatch`. Недостающие папки создаются, относительное значение
отсчитывается от корня репозитория, так что здесь и в терминале оно означает одно место.

Проект, который патчит чужой код, называет этот код в `upstream` и держит патчи отдельным
деревом:

```jsonc
{ "version": 2, "upstream": "..", "generate": { "out": "patches" } }
```

С таким конфигом в `src/brave` патч для `src/chrome/browser/ui/browser.h` —
`src/brave/patches/chrome/browser/ui/browser.h.hatch`. `"upstream": "."` — та же раскладка
внутри одного репозитория.

Решает ядро, а не расширение: расширение пишет туда, куда указал сервис, — туда же, куда
записал бы CLI.

Каждый патч открывается шапкой — до первой пустой строки:

```
Hatch: 1
Target: src/a/b.cc
Generated-From: 3b18e512dba79e4c8300dd08aeb37f8e728b8dad
Generated-By: hatch 0.4.0
Grammar: tree-sitter-cpp@0.23.4
```

`Target` — файл, для которого патч; по нему ядро находит код патча раньше дерева патчей и
`out`. Патч, написанный руками, без `Target` связывается по имени и месту; если ни то ни
другое не помогает, патч говорит об этом на первой строке — допишите туда строку `Target:`.

## Заметки к ханкам

Блок `# note` … `# end` прямо перед `# match` — ваш комментарий к этому ханку: проза с
любого столбца, без отступа, сопоставление её не читает.

```
# note
Повтор оставить: после рестарта сервер теряет первый запрос.
# end

# match cpp
    ...
```

Расширение рисует заметки приглушённым курсивом, как комментарии. Ханк, который никуда
не лёг, подсвечивается красным фоном, ханк, текста которого в коде больше нет, — жёлтым,
оба с меткой на полосе прокрутки; причина — в подчёркивании и в Problems. У ханка не
больше одной заметки, а текст между ханками вне заметки — ошибка разбора. Заметкам нужен
hatch 0.4: старые ядра такой патч не принимают. `generate` заметок не пишет, поэтому
перегенерация патча их стирает.

## Настройка

Два слоя, и они отвечают на разные вопросы.

### Политика проекта — `hatch.config.json`

Сколько контекста несёт порождённый ханк — свойство **проекта**, а не отдельного
разработчика, поэтому живёт в файле, который едет вместе с репозиторием: тогда из одной
и той же пары версий получается один и тот же патч в терминале, в редакторе и в CI.

Расширение читает его ровно так же, как CLI: поиск начинается от папки редактируемого
файла и идёт вверх, останавливаясь на корне репозитория, — конфиг выше репозитория не
применяется никогда.

**Hatch: Init Config** создаёт его в корне репозитория и открывает (нужен hatch с
протоколом 4): новейшая схема, только `$schema` и `version` — все настройки остаются
встроенными, пока вы их не добавите. Текст составляет ядро; в недоверенном workspace
ничего не пишется.

```jsonc
{
  "version": 1,
  "generate": {
    "parents": { "min": 2 },
    "siblings": { "min": 1, "max": 8 },
    "bridgeGap": 2
  }
}
```

Все ключи, что на что они разменивают и значения по умолчанию описаны один раз — в ядре:
[Anchoring options и Configuration в README Hatch](https://github.com/Danil-Varakin/hatchTs#configuration).

### Недоверенный workspace

Патчи генерируются и навигация работает, но workspace не выбирает, куда пишутся патчи:
его собственная настройка `hatch.out` не действует, а патч, который его
`hatch.config.json` отправляет за пределы workspace, пишется только после вашего
подтверждения.

### Настройки редактора — ваше локальное переопределение

Каждый ключ выше доступен и настройкой редактора, чтобы можно было попробовать что-то, не
трогая общий файл. Приоритет тот же, что у флага командной строки над файлом конфигурации:

```
встроенные дефолты  <  hatch.config.json  <  настройки редактора
```

| Настройка | Ключ конфига |
|---|---|
| `hatch.out` | `generate.out` |
| `hatch.language` | `generate.language` |
| `hatch.exact` | `generate.exact` |
| `hatch.bridgeGap` | `generate.bridgeGap` |
| `hatch.parents.min` | `generate.parents.min` |
| `hatch.parents.max` | `generate.parents.max` |
| `hatch.parents.detail.base` | `generate.parents.detail.base` |
| `hatch.parents.required` | `generate.parents.required` |
| `hatch.siblings.min` | `generate.siblings.min` |
| `hatch.siblings.max` | `generate.siblings.max` |
| `hatch.siblings.detail.base` | `generate.siblings.detail.base` |
| `hatch.base.head` | `generate.base.head` |
| `hatch.base.branch` | `generate.base.branch` |
| `hatch.base.commit` | `generate.base.commit` |
| `hatch.base.eol` | `generate.base.eol` |

Три настройки `hatch.base.*` называют базу целиком, как флаг git в командной строке:
любая из них заменяет `generate.base` конфига полностью.

**Настройка, которую вы не трогали, в ядро не посылается вовсе** — она не может молча
перебить конфиг проекта. Заданная явно — пусть даже тем же значением, что стоит по
умолчанию, — она выигрывает для вас.

Что откуда взялось, пишется в журнал при каждом запуске:

```
config: /repo/hatch.config.json applied generate.parents.min; overridden by editor settings: generate.bridgeGap
config: none, built-in defaults only
```

Ради этой строки всё и сделано: настройка, которая молча не сработала, — худший вид
отказа.

## Известные ограничения

- **Применения пока нет.** Расширение порождает, проверяет патчи и переходит по ним;
  применить патч к файлу пока можно `hatch apply` в терминале.
- **Перегенерация стирает заметки.** `generate` не пишет блоки `# note`, поэтому
  перегенерация теряет их и ханки, написанные руками; диалог перед ней предупреждает.
- **Один файл — один патч.** У файла один `.hatch`; второго патча рядом не бывает.
- **Большие файлы со множеством правок** могут генерироваться минутами; отменить можно в
  любой момент из уведомления с прогрессом.

## Разработка

`npm install` приносит ядро тарболом релиза, названным в `package.json`:

```bash
npm install        # ядро, из его релиза на GitHub
npm run build      # бандл в dist/extension.cjs
npm run watch      # пересборка на изменение
npm run check      # тайпчек и тесты
npm run test:e2e   # сквозные тесты, в настоящем VS Code
```

Против ядра, которое правите сами, положите клон рядом и дайте ссылку, не записывая её в
манифест:

```
some-dir/
  HatchTS/                  ядро — npm install && npm run build
  HatchVSCodeExtension-/    этот репозиторий
```

```bash
npm install --no-save ../HatchTS   # node_modules/hatch — ссылка на клон
```

Тогда всё здесь идёт против `HatchTS/dist`: после правки или `git pull` там сначала
`npm run build` в нём. `npm install` без флага возвращает выпущенное ядро.

Дальше F5 либо запуск окна разработки напрямую:

```bash
code --extensionDevelopmentPath=. /путь/к/проекту
```

Правки кода и манифеста подхватываются только после **Developer: Reload Window** в окне
с заголовком *Extension Development Host*.

Правила этого репозитория — диапазон протокола, настройки редактора как зеркало конфига —
в [CONTRIBUTING.ru.md](./CONTRIBUTING.ru.md); как устроено расширение — в
[ARCHITECTURE.md](./ARCHITECTURE.md); что менялось в каждом выпуске — в
[CHANGELOG.md](./CHANGELOG.md); как сообщить об уязвимости — в
[SECURITY.md](./SECURITY.md).

### Сборка пакета

Ядро запускается из `node_modules/hatch`, и его зависимости должны лежать рядом, поэтому
пакет собирается против выпущенного ядра — того, которое названо в `package.json`:

```bash
npm install             # выпущенное ядро
npm run package         # бандл, проверка состава, затем hatch-vscode-<версия>.vsix
npm run test:packaged   # ставит этот .vsix в одноразовый профиль и гоняет в нём набор
```

`npm run package` останавливается, если `node_modules/hatch` — ссылка на клон
(`npm install --no-save ../HatchTS`): vsce отказывается от пути выше корня пакета, а
ссылка принесла бы сборочное дерево ядра и его dev-зависимости вместо его пакета. Перед
