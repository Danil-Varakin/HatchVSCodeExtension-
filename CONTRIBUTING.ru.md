# Как участвовать

> English version: [CONTRIBUTING.md](./CONTRIBUTING.md)

Расширение — клиент сервиса hatch. Правила для всех трёх чисел hatch живут в ядре, в
[VERSIONING.md](https://github.com/Danil-Varakin/hatchTs/blob/main/VERSIONING.md), и
обязательны здесь так же, как там. Ниже — то, что касается этого репозитория. Как
устроен код — в [ARCHITECTURE.md](./ARCHITECTURE.md).

## Подготовка

```bash
npm install        # ядро — тарбол релиза, названный в package.json
npm run check      # тайпчек и тесты
npm run test:e2e   # сквозные тесты, в настоящем VS Code
```

F5 запускает *Extension Development Host* (`.vscode/launch.json`, сборка — задачей
`build`). Правки кода и манифеста подхватываются после **Developer: Reload Window** в этом
окне.

Против ядра, которое правите сами, положите клон рядом и отдайте его npm, не записывая в
манифест:

```
some-dir/
  HatchTS/                  git clone …/HatchTS && npm install && npm run build
  HatchVSCodeExtension-/    этот репозиторий
```

```bash
npm install --no-save ../HatchTS   # node_modules/hatch — ссылка на клон
```

Тогда всё здесь идёт против `HatchTS/dist`: после правки или `git pull` там сначала
`npm run build` в нём. `npm install` без флага возвращает выпущенное ядро — а
`npm run package` на ссылке отказывается работать, потому что `.vsix` не несёт путей выше
своего корня.

Пакет собирается только против выпущенного ядра:

```bash
npm run package         # бандл, проверка состава, затем hatch-vscode-<версия>.vsix
npm run test:packaged   # ставит этот .vsix в одноразовый профиль и гоняет в нём набор
```

## Единственное архитектурное правило

**В расширении нет логики Hatch.** Оно не разбирает `.hatch`, не сопоставляет шаблоны, не
переносит позиции между версиями файла, не вычисляет, куда кладётся патч и к какому
файлу он относится. Оно спрашивает ядро (`generate`, `resolve`, `apply`, `config`,
`pair`) и показывает ответ. Вторая копия любого из этих правил молча разойдётся с ядром
и начнёт выдавать правдоподобные, но неверные координаты. Если функции, кажется, нужно
такое правило — правило идёт в ядро и приходит в расширение через протокол.

И второе: **никогда не прыгать «куда-то похоже».** Любой ответ — точное место, место,
названное приблизительным, или отказ с причиной и следующим шагом.

## Диапазон протокола (R7–R9)

- Расширение объявляет **диапазон** `SUPPORTED_PROTOCOL = { min, max }` в
  `src/service/protocol.ts`: `max` — новейший протокол, против которого оно написано и
  проверено; `min` — старейшее ядро, с которым оно ещё работает.
- Совместимо с ядром, если диапазоны пересекаются: `min ≤ protocol` и
  `protocolMin ≤ max`. Ядро без `protocolMin` (протокол 2 и старше) читается как
  `protocolMin = protocol`.
- **Проверка равенством запрещена** (R9): она ломает расширение на каждом подъёме
  протокола, даже совместимом.
- `max` поднимается только после прогона тестов против ядра с этим протоколом. `min`
  поднимается только когда расширение начинает пользоваться тем, чего у старых ядер нет, —
  и тогда это ломающее изменение для расширения.
- Рабочий протокол — `min(protocol ядра, max)`, ничего новее не используется.
- Пути в запросах — только абсолютные (протокол 2): у сервиса нет своей рабочей папки.
- Типы протокола реэкспортируются из `hatch/protocol`, а не копируются: расхождение с
  ядром — ошибка компиляции, а не тихий дрейф.

## Настройки редактора повторяют конфиг (E1)

- У каждого ключа `generate.*` из `hatch.config.json` — настройка `hatch.*` с тем же путём
  без `generate.` (`generate.base.eol` → `hatch.base.eol`), с тем же смыслом и теми же
  значениями. По умолчанию она не задана (`null` или пустая строка), и тогда решает
  конфиг; заданная — перекрывает конфиг только для этого человека, как флаг CLI.
- Настройка выходит **в том же выпуске**, что и поддержка схемы конфига, в которой
  появился ключ. Удалён или переименован ключ в ядре — так же с настройкой.
- Настроек `hatch.*`, которых нет в конфиге, не заводить. Исключение вписывается сюда с
  причиной до того, как настройка выходит.
- Значение по умолчанию — как в ядре, кроме перечисленного здесь, с причиной:
  - `base.eol`: если не задано ни настройкой, ни конфигом, расширение шлёт `worktree`, а
    ядро и CLI по умолчанию берут `repository`. Причина: расширение сравнивает с
    буфером, а буфер — это файл с диска; при `core.autocrlf` база с окончаниями
    репозитория сделала бы изменённой каждую строку.
- `test/settings-config.test.ts` сверяет `package.json` с новейшей схемой конфига ядра, с
  которым собрано расширение, а настройки, запрещённые недоверенному workspace, — с теми,
  что код там игнорирует.

## Тесты

`npm test` запускает `node --test` по `test/**/*.test.ts`, без редактора:

- **Чистые модули** — выбор ханка, подрезка краёв, хранилище таблиц, вердикты, настройки
  — тестируются отдельно. Поэтому новую логику держите в чистых модулях:
  склейка с редактором остаётся тонкой.
- **Против настоящего ядра** — клиент, `config`/`pair`/`resolve`, координаты, на которые
  опирается навигация. Координаты никогда не проверяются на рукописных фикстурах:
  ханк, написанный руками, может согласиться с тестом и разойтись с сервисом.
- **Против подставного ядра** (`test/fixtures/fake-service.mjs`) — только то, что
  настоящее не сделает по заказу: `generate`, который считает до отмены, ядро без
  `cancel`, ядро, которое не останавливается.

`npm run test:e2e` запускает расширение в настоящем VS Code (`@vscode/test-cli`; первый
запуск скачивает VS Code в `.vscode-test/`). `test/e2e/fixture.mjs` при каждом запуске
делает свежие workspace во временной папке — репозиторий с git-базой, проект над
`upstream`, папку без git и workspace `quiet`, где нет ничего от hatch, — а тесты в
`test/e2e/*.e2e.ts` управляют расширением только через его команды и то, что показывает
VS Code: линзы, Problems, Outline, строку состояния, диффы, окна сообщений (на них отвечает
заглушка). Расширение отдаёт тестам из `activate` несколько хуков только для чтения
(`HatchTestApi`): сколько ядер запущено, ворота, текст строки состояния, таблица. Функция,
которая что-то показывает в редакторе, приходит вместе со своим сквозным тестом.

Тестов внутри VS Code (`@vscode/test-electron`) пока нет; то, что требует редактора, —
линзы, закрытие вкладок, наблюдатели за диском — проверяется руками в окне разработки.

## Перед тем как изменение войдёт

- `npm run check` (тайпчек и тесты) зелёный, против свежесобранного ядра.
- `README.md` и `README.ru.md` меняются вместе, `CONTRIBUTING.md` и `CONTRIBUTING.ru.md`
  — тоже.
- Видимое пользователю изменение — строка в `CHANGELOG.md` в разделе *Unreleased*,
  ломающие изменения первыми.
- Новая настройка — по E1; новый метод или поле протокола используется только после того,
  как его покрывает `max`.
- Идентификатор команды пишется в `package.json` и в `src/commands/ids.ts`, больше нигде.

## Выпуски

- `CHANGELOG.md` называет для каждого выпуска четыре числа: версию расширения, диапазон
  протокола, на котором оно говорит, схему конфига, которую повторяют его настройки, и
  формат патча, который подсвечивает его грамматика.
- **Версия расширения.** До 1.0.0 любая новая функция и любое ломающее изменение поднимают
  minor (0.1.0 → 0.2.0), одно исправление — patch (0.1.0 → 0.1.1). С 1.0.0 — semver:
  ломающее — major, функция — minor, исправление — patch.
- **Что ломает расширение:** подъём `min` диапазона протокола (старый hatch перестаёт
  работать); удаление или переименование настройки `hatch.*`, id команды или сочетания
  клавиш; отказ читать схему конфига или формат патча. Каждое пишется в CHANGELOG под
  *Breaking* с тем, что делать.
- Подъём `max` диапазона протокола, настройка для нового ключа конфига (E1), новая команда
  — функция.
- `.vsix` несёт ядро, с которым его проверили; версия ядра называется в записи CHANGELOG, а
  `max` поднимается только после `npm run check` и `npm run test:e2e` против него (R7).
- Выпуск расширения, говорящий на новом протоколе, выходит раньше или вместе с hatch,
  который поднимает `protocolMin` (VERSIONING.md, S3); таблица *Clients* там
  обновляется вместе с ним.
